**T-1 — TypeScript number-branch injection (sibling of the S-1 str() fix):** `convert_param_to_ts_value` returned `str(raw_value)` for number/integer params — a model-supplied string was emitted verbatim into TypeScript code. Fixed both sides: `start_server` records `os.environ["HOST"] = host` before the server starts, and the middleware re-resolves HOST once on first dispatch (a wildcard/LAN env host recomputes enforcement and the allowed-host set; the constructor default still covers the no-flag path). The JS-reserved-words note (names like `var`/`let` produce a syntax error, not an injection; schema membership bounds the names) — noted, no change.

The crafted argument name executed as code through POST /v1/tools/run on the unfixed image, surfacing the sentinel `RuntimeError: RIG26D_INJECTION_EXECUTED` in the tool error response.

**Control design note (why a sentinel raise, not a marker file):** the first 26d control checked for a host-side marker file — but the injected code runs INSIDE the container under the Landlock sandbox, where writes outside the sandbox's grants fail silently; the marker never appeared on EITHER image (verified: the unfixed run created no marker although the hostile name WAS pasted into the generated script — the injection ran; the exec was blocked). The sentinel raise proves execution in-band, in the response body. The verdict also had to be ORDERED (rejection first): the choke point's rejection message QUOTES the crafted name, whose repr embeds the sentinel text — an unordered sentinel grep false-failed the FIXED image. The injection verdict requires the `RuntimeError: RIG26D_INJECTION_EXECUTED` raised-error form, which only an actual execution produces.

Getting here cost three rig-writing iterations (curl status from the mktemp path; impossible empty-tool_return condition; the sentinel/rejection ambiguity), each caught by the rig itself — the rig-as-rig discipline: a check that fails for the wrong reason is itself a bug.
