## Environment findings (pre-existing, NOT .39 regressions — verified against v0.16.38 baseline)

- **sqlite-path server startup fails locally**: `create_default_organization_async` → `db_registry.async_session()` raises `RuntimeError: generator didn't stop after athrow()` (greenlet/contextlib interplay, Python 3.12.12, sqlite branch). **Reproduced identically on v0.16.38 (05a7d0af5) in a fresh worktree/venv** — not caused by .39. CI and all consumers run PG (the rig's PG-backed server starts fine, 21/21). LEDGERED: local-dev-only sqlite startup bug, fix out of .39 scope.
- **Full-suite run-completion blocker**: `tests/sdk/conftest.py` polls `/v1/health` with no requests timeout; uvicorn binds its socket before app startup completes, so when startup fails the poll connects to the lingering socket and parks forever (0% CPU event-loop wedge, immune to pytest-timeout's signal method under gevent). Fixed in .39 with `timeout=5` — test infra, not product code. The F2-era baseline (1265 errors) almost certainly contains the sdk tests erroring on the same failed startup; the wedge is the only new behavior.
- **Locust monkey-patch wedge (root cause of the moving suite wedges)**: `tests/locust_test.py` was a locust load-test script (zero pytest tests) named with a pytest-collected prefix. Importing locust monkey-patches the ENTIRE process with gevent; any later test doing patched-socket I/O from a thread can park forever on a hub nobody services (two different wedge sites observed across runs — the wedge moves with timing). Renamed to `tests/locustfile.py` (locust's own default filename): pytest no longer imports it, locust still finds it. Upstream slop, present since 2025-09; the F2 baseline run got lucky on the race.
- **Baseline comparison caveat**: the F2 baseline FAILED list was generated 2026-11-22; the sdk-poll fix changes those tests from "wedge" to "error" — expected in the FAILED/ERROR diff, not a regression.

## Rig-caught bugs this release (the rig doing its job)

- **Quick-start witness, two iterations (B-13)**: (1) `ReasoningMessage` has no `.content` attribute — message-shape assumptions in the witness crashed before extraction; (2) `AssistantMessage.content` is `Union[str, List[parts]]` — iterating a plain-string content yields characters with no `.type`, silently producing zero text chunks. Both rig-caught, both fixed in the witness (defensive shape handling). LESSON: SDK response shapes are unions — witness code must handle every arm, and the rig's live run is what catches it (unit tests can't see the real response shape).
