### S-2/S-7 — internal datastore trust (the chain's remaining links)

- Internal Postgres: `POSTGRES_HOST_AUTH_METHOD=scram-sha-256` + `POSTGRES_INITDB_ARGS=--auth-local=scram-sha-256 --auth-host=scram-sha-256`, a generated random password at first boot (not the baked-in `letta`), and `listen_addresses=''` (Unix socket only) or 127.0.0.1.
- Internal Redis: `--bind 127.0.0.1 --requirepass <random>`.
- Sandbox: loopback datastore ports refused for tool TCP even when network is on (Landlock per-port where enforced; seccomp-level destination control is not possible — document the residual and gate on the S-14 per-port work where needed).
- README quickstart: `-p 127.0.0.1:5433:5432` + generated password; stop EXPOSEing 5432/6379.
- **Rig check 27 + R-2 acceptance (REVISED per round-2-instructions — condition 2 was WRONG: Landlock does not mediate connect() to a pathname Unix socket):**
  1. From a network-enabled tool: connecting to 127.0.0.1:5432 and :6379 WITHOUT the password fails; reading the generated passwords from `/proc/*/environ`, `/proc/*/cmdline` and the password file FAILS; therefore connecting WITH them is impossible. Positive control: the same probe run in a deliberately unsandboxed process reads the password.
  2. **The Unix socket — SECCOMP does the blocking, not Landlock:** seccomp argument filters deny `socket()` with `AF_UNIX`, `AF_PACKET`, `AF_NETLINK` and `SOCK_RAW` for network-enabled tools, and deny `SOCK_DGRAM` unless explicitly allowed (AF_INET/AF_INET6 SOCK_STREAM only). Rig probes: a network-enabled tool's attempts to open a Unix socket, UDP and raw sockets all FAIL, with positive controls. Postgres socket directory + credentials must be inaccessible to the sandbox uid by ordinary file permissions.
  3. **Port allowlist as defense in depth:** network-enabled tools get a default Landlock port allowlist of `{80, 443}` plus a configured list (Delta adds 8000 for its backend). 5432/6379 blocked by omission. **S-14's port semantics fold into S-2 here** (port-0 is not a wildcard; org config must MERGE not replace for network tools; block `io_uring_*`). NOTE: the TCP port allowlist does NOT cover UDP — condition 2's socket-family filter is what closes that.
  4. **The separate sandbox uid (S-13) is REQUIRED for S-2, not a fallback.** Postgres and Redis credentials, and the socket directory, must be inaccessible to that uid by ordinary file permissions. (Today the image runs as root with no separate sandbox uid — S-13 Read; round-2 R2A-3 also pulls it forward for truncate/chmod/chown.)
- **README/Dockerfile correction (R2A-4):** "Landlock blocks UDP" is FALSE for network-enabled tools (seccomp blocks socket() only when network is OFF — _landlock_ctypes.py:299 verified). The DNS-over-TCP justification at Dockerfile:111 and README:251 gets rewritten to the seccomp socket-family filter as the actual mechanism.

### R2A-1 — HIGH: policy/approval check different values than the tool receives (VERIFIED by two reviewers)

The policy engine checks the RAW model args; the executor then REWRITES them — server-side coercion (ast_parsers.py:146-155) json.loads/literal_evals EVERY string regardless of target type, then arg_type(value); the in-sandbox coercion block and S-1's array/object decode do it again. A model bypasses any argument-level deny/approval rule by stringifying or escaping: `"\u0044ROP TABLE users"` passes a `pattern: "DROP|TRUNCATE"` deny and the tool executes `DROP TABLE users`. The reviewer's repro used the README's OWN example policy. Numeric caps fail open in NORMAL use (local models send numbers as strings).

**Fix:**
1. **Canonicalize once, server-side, BEFORE any security check.** Run the coercion (server-side `_prepare_function_args` + array/object decode) first, then hand that ONE dict to the canary check, the policy check, the approval request, and the executor. No path checks raw args after this.
2. **Don't decode str-typed parameters.** `coerce_dict_args_by_annotations`: the json.loads/literal_eval fallback skips values whose resolved annotation is `str`.
3. **Deny and approval rules fail closed on type mismatch** (`gt` against a non-number counts as a match for deny/approval rules, or the call is rejected when its type doesn't match the schema).
4. README example goes case-insensitive (`(?i)`).
5. Sibling scan (the mechanism has MANY call sites): server-side coercion, in-sandbox coercion, S-1's array/object decode, approval display, `_resolve_field`/`gt`/`lt`/`matches`/`contains`/rule-`pattern` in policy.py.
6. Rig check: the reviewer's escaped (`"\u0044ROP..."`) and implicit-concat (`"DR" "OP..."`) payloads are DENIED, with a control showing the plain form is denied too.
7. Regression test: stringified and escaped variants through `check_policy` then `_prepare_function_args`, asserting the same decision either way.

### R2S-1 — HIGH: `.af` import re-binds provider keys to the file's endpoints

The imported llm_config/embedding_config keep the FILE's `model_endpoint` (free-form, unvalidated — llm_config.py:160) and `provider_name`; on the agent's first step the server attaches the org's provider key (BYOK decrypt via get_byok_overrides_async, or OPENAI_API_KEY) to `base_url=<attacker URL>`. Same `base_url=llm_config.model_endpoint` pattern in deepseek/groq/fireworks/minimax/baseten clients.

**Fix:** on import, DISCARD the file's endpoint and provider binding — `model_endpoint`, `provider_name`, `provider_category`, and the embedding equivalents — and rebuild from a handle (`llm_config.handle` or the server default) through `get_llm_config_from_handle_async`; refuse the import if the handle is unknown. Separately: reject `model_endpoint`/`embedding_endpoint` values that don't match the selected provider's configured base URL whenever a server-held key would be attached (covers PATCH /v1/agents/{id} too). Sibling scan: every client that sends a key to `llm_config.model_endpoint`.

### R2S-2 — HIGH: `.af` import re-points existing MCP servers, keeping credentials

Import upserts every `mcp_servers[]` entry by name (agent_serialization_manager.py:546-556, unconditional — `override_existing_tools` doesn't gate it); the update carries the file's `server_url` while `token_enc`/`custom_headers_enc` SURVIVE, so the stored credentials go to the attacker's URL on the next connection. Verified by the reviewer's demo.

**Fix:** import NEVER updates an existing MCP server — skip (or create `<name>_imported` with NO credentials). Sibling (beyond import): ANY MCP server URL change, through the API too, clears the stored token and custom headers and requires re-entry unless new credentials arrive in the same request. S-12's `override_existing_tools` flip does NOT cover this — separate item. Import reports MCP servers in its "would change" list.

### R2S-3 — MCP tool sync hijacks existing tools by name

A malicious/changed MCP server's tool list upserts by (name, organization_id) ON CONFLICT DO UPDATE — overwriting EVERY column of any existing tool (custom, built-in) with `tool_type=EXTERNAL_MCP` + the attacker server's tag. Every agent attached to the original tool now calls the attacker with its arguments.

**Fix:** MCP sync never overwrites a row whose `tool_type` isn't EXTERNAL_MCP or whose `metadata_.mcp.server_id` differs — skip or rename (`server__tool` namespacing, or refuse-and-report the collision). Reserve built-in tool names. Refresh additions opt-in or listed for approval.
