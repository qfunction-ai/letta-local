## Batch A — the ER definition's named first pieces

### A1. Aged-data fixture + N−1 → N upgrade rig stage (ER-1.3, ER-2.1)

The item that matters most. It would have caught the FK-cascade bugs of v0.16.23/24 and the sqlite-branch wedge of v0.16.38 before consumers hit them.

- **Fixture:** a rig script seeds a database by booting the PREVIOUS release's published image (digest-pinned; for .41 that's v0.16.40 `@sha256:b02e97ff…3b5a`) and creating realistic content: several agents (V3), a user, secrets (one plaintext-legacy row via the E-1 seeding path, one marked), messages, a custom tool, archival memory passages, a policy. Seed via the API + `POST /messages/capture` (LLM-free, no Ollama contention) plus psql for the legacy-row edge.
- **Stage:** `compose down` (volumes persist), `up` with the N image, then assert: health green; the seeded agents/messages/passages are present and readable; secrets readable (marked rows decrypt; the legacy row is reported by the startup report); **a real tool call works end-to-end** (run_first rule, no LLM dependency where possible — the RC-8-style custom tool).
- **Parameterization:** `PREV_IMAGE` and `CUR_IMAGE` env vars so every future release re-runs the stage with N−1 = the previous tag. Rig check 25.
- **Proof:** stage output (seed counts, post-upgrade read-back counts, tool-call result) in the evidence doc.

### S-2/S-7 — internal datastore trust (the chain's remaining links)

- Internal Postgres: `POSTGRES_HOST_AUTH_METHOD=scram-sha-256` + `POSTGRES_INITDB_ARGS=--auth-local=scram-sha-256 --auth-host=scram-sha-256`, a generated random password at first boot (not the baked-in `letta`), and `listen_addresses=''` (Unix socket only) or 127.0.0.1.
- Internal Redis: `--bind 127.0.0.1 --requirepass <random>`.
- Sandbox: loopback datastore ports refused for tool TCP even when network is on (Landlock per-port where enforced; seccomp-level destination control is not possible — document the residual and gate on the S-14 per-port work where needed).
- README quickstart: `-p 127.0.0.1:5433:5432` + generated password; stop EXPOSEing 5432/6379.
- **Rig check 27**: a network-enabled tool's connections to 127.0.0.1:5432 and :6379 FAIL, with an unfixed-first positive control. Per the findings doc, the .41 release check covers this evidence specifically.

## Batch B — cheap ER wins

### B1. CI migration-agreement check (ER-1.1)

- New CI job (or a step in an existing workflow): boot PG, `alembic upgrade head`, then `alembic autogenerate` against the models — the diff must be **empty**. Non-empty diff fails CI.
- Catches model/migration drift at PR time instead of at container boot (the f6cd5a1e519d lesson: the unit suite never runs alembic env.py, only the container does).
- **Proof:** the workflow exists and runs green on the .41 tag.

### B2. "API changes" changelog section (ER-5.1)

- Every release evidence doc gains a section titled "API changes" (empty = "none"). Retroactively note .40's (nothing breaking; behavior notes were in the consumer notice). Template line added to the release process.
- **Proof:** the section exists in the .41 evidence doc.

### B3. Key-loss story, written down + witness (ER-3.2)

- README section: what is lost on key loss (all `enc:v1:` secrets — unrecoverable by design), what can be rebuilt (agents, messages, memory — everything that isn't a secret), and the guard against silently making a second key.
- Witness: delete the key from a running install's env, restart → startup must REFUSE (or report loudly and refuse secret reads — behavior verified during implementation, the README documents what actually happens, not what we wish happens).
- **Proof:** README section + witness output in the evidence doc.

### B4. Org-ownership schema check (ER-4.2)

- A test that walks every SQLAlchemy model: every table carries `organization_id` or has a documented exemption (ledgered in the test file as an allowlist). Plus one cross-org query test: an entity created under org A is invisible to org B's queries.
- LettaLocal already has organization_id everywhere — this is a regression guard, not a retrofit.
- **Proof:** the test in the suite, green.

### B5. Migration irreversibility audit (ER-1.2, partial)

- Audit every existing migration: can it downgrade? Those that can't get `down_revision`-preserving irreversible markers with a reason, and the release notes list them. Full upgrade→downgrade→upgrade testing on the aged fixture is NOT in .41 (deferred; the fixture from A1 makes it cheap in .42).
- **Proof:** the audit list in the evidence doc.

### B6. Key-rotation design doc (ER-3.3 — design only)

- A `v2` marker scheme, re-encryption-under-new-key command design, dual-key read window, and the migration from `enc:v1:`. Design doc, reviewed; implementation deferred under ER Part 2 ("key rotation implementation").
- **Proof:** the reviewed design doc.
