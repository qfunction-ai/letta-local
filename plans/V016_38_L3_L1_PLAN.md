## Why L-3 and L-1 ship together

Verified in code at 4047471ac:

- The REST API has no auth on localhost. Sandboxed tool code can call any endpoint, including rewriting its own sandbox config and policy (demonstrated live by rig check 20: PATCH → 200).
- `app.py:175`: `random_password = os.getenv("LETTA_SERVER_PASSWORD") or generate_password()` — the password lives in the server process environment.
- `base.py:617`: `env = os.environ.copy() if is_local else {}` — local sandboxes inherit that environment.

Therefore password auth ALONE does not close L-3: tool code reads `LETTA_SERVER_PASSWORD` from its own inherited environment and calls the API with it. The tripwire would go green while the escape still works. L-1 (allowlist) is required in the same release, or L-3 is theater.

## W2 — L-1: allowlist for local sandbox environments

Replace `env = os.environ.copy() if is_local else {}` in `_gather_env_vars` (base.py) with an explicit allowlist for the `is_local` case:

```python
LOCAL_SANDBOX_ENV_ALLOWLIST = {"PATH", "LANG", "LC_ALL", "LC_CTYPE", "TZ", "SSL_CERT_FILE", "SSL_CERT_DIR"}
env = {k: os.environ[k] for k in LOCAL_SANDBOX_ENV_ALLOWLIST if k in os.environ} if is_local else {}
```

`HOME` and `TMPDIR` are NOT inherited (reviewer ruling): they are set to the per-execution sandbox directory, so libraries writing ~/.cache or temp files get a writable location inside the grant and the tool never learns the server's home path. `HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY` are NOT in the allowlist — proxy URLs carry credentials; network tools behind a proxy get them through the sandbox env-var channel, where R-1's value scrub still applies.

The layered channels stay exactly as they are — they are the SANCTIONED credential path:
- global sandbox env vars from DB, provided sandbox env vars, agent state env vars, additional runtime vars (base.py:620-641);
- injected `LETTA_AGENT_ID`, `LETTA_AGENT_FILES_DIR`, `LETTA_STAGING_DIR`, `LETTA_PROJECT_ID`, `LETTA_TOOL_ID`;
- spawn-side additions (`LETTA_SANDBOXED_TOOL_EXECUTION`, `PYTHONWARNINGS`, `NO_COLOR`, `TERM`, `VIRTUAL_ENV`, `PATH` prepend).

Never in the tool environment: `LETTA_SERVER_PASSWORD`, `LETTA_PG_URI`, `LETTA_ENCRYPTION_KEY`, provider API keys, and anything else anyone adds later. Allowlist fails closed; a denylist would fail open on the next secret someone adds (reviewer ruling, accepted).

Verification items:
- `_prepare_venv` and the venv spawn path work under the allowlist (they receive the same `env` — confirm pip/venv don't need vars outside it).
- A test asserting the allowlist: build env with `LETTA_SERVER_PASSWORD` et al. set in `os.environ`, assert absent from the gathered env; assert the sanctioned channels still land.

## R-1 — Scrub by VALUE across every channel (reviewer-required)

The allowlist only stops secrets arriving through `os.environ`. The four layered channels (DB global, provided, agent, runtime) pass values through unchanged — and `base.py:365-385` builds the injected Letta client from `LETTA_API_KEY`, so an operator who puts the server password into a sandbox env var reopens L-3 through the sanctioned path. The rig wouldn't notice (it doesn't set it). Verified in code.

Required:
1. After all layering in `_gather_env_vars`, drop any variable whose VALUE equals the server password, the Postgres URI, or the encryption key. Log the key NAME, never the value.
2. Reject with 400 any API write of a sandbox/agent env var whose value equals the server password.
3. Check 20 additions: set the password as a sandbox env var via the API → expect 400; set it directly in the DB → expect the tool environment not to contain it.
4. README: the server password must never be given to tools. Tools that need the API need their own scoped credential — does not exist yet, v0.16.39 design item.

## W3 — L-3 minimal: secure mode ON by default

Decision: `LETTA_SERVER_SECURE` defaults to **true** in v0.16.38. Rationale: opt-in secure mode leaves every existing deployment open — the tripwire passes (the rig enables it) while consumers stay vulnerable. A default-on switch is the only version of "minimal L-3" that closes the hole for real deployments.

Per reviewer ruling:
- Secure unless `LETTA_SERVER_SECURE` is exactly `false` (not "not true" — unset means secure).
- Insecure start logs a startup WARNING naming the risk.
- The rig FAILS if the server under test is in insecure mode.
- `check_password.py`: both header comparisons use `hmac.compare_digest` (current `==` leaks timing — minor over localhost, one-line fix).
- No websocket routes exist (verified) — `BaseHTTPMiddleware` covers every route.

- Middleware already exists (`CheckPasswordMiddleware`): `Authorization: Bearer <password>` or `X-BARE-PASSWORD: password <password>`; health/ready endpoints exempt (verified — the rig's health checks and version gate are unaffected).
- Password source: operator sets `LETTA_SERVER_PASSWORD`. If unset, generate and write to `${LETTA_DIR}/server_password` (mode 0600) — log the file PATH, never the value.

## W5 — /proc readability: verify, don't assume

Landlock read grants default to `/usr, /lib, /lib64, /etc, /app, /extra-packages, /data/config` (sandbox_config.py:109) — `/proc` is NOT granted, so `/proc/<server pid>/environ` should already be denied to sandboxed processes (structurally sound). Verify live during implementation — the requirement is that a tool cannot read OTHER processes' environment or command line:
- `/proc/1/environ` — must fail;
- `/proc/<server pid>/environ` and `cmdline` — must fail;
- a scan of `/proc/*/environ` — must fail.

`/proc/self/environ` shows only the tool's own already-filtered environment (post-R-1) — harmless, NOT a requirement (reviewer ruling). If any other-process read succeeds, that's a new finding and the read-grant set needs a look; do not ship W2/W3 claiming closure without these checks passing.

## R-2 — Inventory the server's calls to itself (reviewer-required)

With secure mode on by default, any server-to-self HTTP path starts getting 401. A silent 401 inside a built-in tool shows up as an agent that "just stopped doing things" — the opaque-failure class. Verified inventory:

- `base.py:365-385` — injected Letta client in sandboxed custom tools, built from `LETTA_API_KEY` env var.
- `builtin_tool_executor.py:77-112` (tool_executor/, not tool_sandbox/ as the review cited) — agent-aware built-in tools, same env var.
- `functions/function_sets/multi_agent.py:15-16` — multi-agent messaging client, `LETTA_API_KEY` + `LETTA_SERVER_URL or http://localhost:8283`.
- `tool_manager.py:75` — LETTA_API_KEY secret placeholder.
- No websocket routes (verified) — nothing else to cover.

Resolution for v0.16.38: these paths run in the SANDBOXED tool process, so in-process credential injection is not possible — and R-1 deliberately scrubs the password value from that environment. Agent-aware/multi-agent tools are therefore **documented broken under secure mode** for .38; each 401 must surface as a visible tool error, not silence. Scoped tool credentials are the v0.16.39 design item (with R-1 item 4). Every path is covered in the full-suite failure-set diff, and the consumer notice names the breakage.
