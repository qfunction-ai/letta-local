## C-2 Container extras trim

The scan covers 858 pins because the container installs `--all-extras`. Some of the worst offenders (nltk in particular) may come only from extras no QFunction product uses.

1. **FIRST (.40's opening move, review change 2): record the extras each consumer needs** — **Delta** via the usual file-based handoff through Ryan (a short request listing candidate extras to drop, asking which ones Delta's code or tools import — agents don't contact each other directly, review answer 3), **Nabla**, **Epsilon**.
2. Drop the rest from the container build (`uv sync` extras list instead of `--all-extras`).
3. **REV 2 (review answer 2): the container's extras and the scan's `uv export` change in the SAME commit** — the scan must always match what's actually installed. Regenerate the baseline from the new export at that commit and record the delta. Entries that disappear because of the trim count as REMOVALS; nothing can be added (shrink-only).
4. Rig must stay green on the trimmed image (the rig exercises the server's real install).

**Witnesses:** consumer extras matrix (written into this plan), Dockerfile diff, scan output before/after with baseline delta, rig run on the trimmed image.

**REV 2 (review change 4): the trim needs a RUNTIME witness, not just a green rig.** Removing an extra fails at runtime, when an optional import is first reached — not at install time. The rig covers core paths, not every optional one:
- **Import smoke test**: import every module reachable from the mounted routers and the tool executors on the trimmed image; fail on any ImportError.
- **Consumers' own checks before adopting the trimmed image**: Delta runs its suite against it; Nabla and Epsilon run theirs at their next re-pin (neither re-pins during filming).
