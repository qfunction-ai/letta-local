### R-5..R-8 (Part B review "should fix", verified by the reviewer)

From `V016_39_PART_B_REVIEW.md` — all four verified by the reviewer (R-5 and its substring table ran live; R-8's pattern scan found no current violations, so it's prevention).

**R-5 Containment scrub minimum secret length.** `_value_carries_secret` does substring matching: a 4-char operator password scrubs `PATH` (contains "bin"), a short password scrubs `LETTA_AGENT_FILES_DIR`. Fails closed (breaks tools, leaks nothing) but confusing, and `validate_env_var_value` 400s benign writes for the same reason. Fix: containment matching only for secrets ≥12 chars; below that, exact match + startup WARNING that the password is short. With the guard in place, add the Postgres password component (`urlparse(pg_uri).password`) to the sensitive set — today only the whole URI matches, so a value carrying just the DB password passes (and without the length guard this would misfire: the compose default password is `letta`).

**R-6 Password file permissions.** `write_text()` then `chmod(0600)` leaves a umask-mode window (typically 0644); a pre-existing loose file is reused unchecked; and there are TWO writers (`server_credentials._write_password_file` + the secure-mode block in `app.py`). Fix: create with `os.open(O_WRONLY|O_CREAT|O_TRUNC, 0o600)`; on read, warn/tighten if group/other bits set; one writer. Also feed the B-5 design doc: under the LOCAL executor (Landlock unavailable), tools run as the server user with no filesystem restriction — they can read `~/.letta/server_password` and `/proc/<ppid>/environ`. B-5 must state plainly that LOCAL is not a security boundary.

**R-7 Embedder no-key fallback fail-closed.** B-2's fallback preset points at the OpenAI cloud endpoint; with no key, `_prepare_client_kwargs_embedding` substitutes a dummy key and the request still goes to api.openai.com (401) — uploaded document chunks leave a machine in a product sold as local. Fix: no key and no explicit config → fail closed with "no embedding model configured". Never default to a cloud endpoint. (Reachability: agent-import path passing `embedding_config=None` is plausible but unproven — the fix doesn't depend on it.)

**R-8 B-1 guard widening.** Add `letta/services/helpers/` to the guarded directories (R-1 lived there). Add patterns: `{**os.environ}`, `os.environ.update/setdefault/pop`, and subprocess/asyncio spawns with NO `env=` (whole-environment inheritance) — with an exemption annotation for remote executors (E2B). Reviewer scanned: zero current violations, so this is prevention.

### E-1 Re-encrypt secrets stored as plaintext (REV 6 — `reencrypt-secrets-plan.md`, verified + approved)

Source: Ryan/Claude plan 2026-11-25; my verification (`E1_REENCRYPT_REVIEW_RESPONSE.md`, all five claims confirmed, zero refutations); reviewer acceptance (`E1_REENCRYPT_REVIEW_RESPONSE-REVIEW.md`, accepted with four additions; marker approved with three conditions). Problem: without `LETTA_ENCRYPTION_KEY`, `Secret.from_plaintext` stores plaintext in the `_enc` column (documented fallback); when a key is later set, nothing re-encrypts those rows — `update_agent`'s reuse logic (agent_manager.py:952-996) rewrites the same plaintext for identical values, and there is no migration. Worse (F-A): on ambiguous rows — high-entropy plaintext that passes the `is_encrypted()` base64 heuristic — the reuse comparison's `get_plaintext_async()` RAISES, so `PATCH /v1/agents/{id}` 500s; the operator can't fix the row through the API at all.

**Build, one commit series:**

1. **Write path** — a value counts as "unchanged" only if it decrypted with the key. Implement as a helper on `Secret` (e.g. `was_decrypted_with_key()`), set by `get_plaintext_async`, recording WHY the plaintext came back (decrypted / fell back / raised) so the manager never re-derives it. Handles both failure modes: decrypt-failed-then-fallback AND decrypt-failed-then-raise (F-A). The next manager to copy the reuse pattern gets it right by default.
2. **`enc:v1:` ciphertext marker** — approved with three conditions:
   - **Downgrade hazard**: after v0.16.40 has written secrets (or after `--apply`), downgrading below v0.16.40 silently breaks those secrets (v0.16.39's read path returns the marked ciphertext as plaintext — garbage credentials, no error). Release notes, README, and the v0.16.40 consumer notice must state: don't downgrade without restoring a pre-upgrade DB backup. `--apply` prints the same warning and requires `--yes`.
   - **Marked reads never fall back**: if a value starts with `enc:v1:` and decryption fails, the read RAISES (wrong key or corruption) — never returns the stored string. Error names the column, never the value.
   - **Version semantics**: `v1` = today's format (salt, IV, tag, ciphertext, base64, today's KDF). Any future KDF/cipher/key-handling change gets `v2`. Key rotation itself is out of scope; the marker is what makes it possible later.
3. **`letta secrets reencrypt`** on the existing typer CLI (`letta.main:app`; run as `docker exec <ctr> letta secrets reencrypt`). Requires a configured key; dry run by default. Dry-run classes: **unmarked-encrypted** (decrypts with the current key — to be marked), **plaintext** (to be encrypted and marked), **ambiguous** (blocks `--apply` unless `--treat-ambiguous-as-plaintext` + `--yes`, which echoes the "no other key has ever been used on this database" statement back). `--apply` rewrites plaintext AND unmarked-encrypted rows in one transaction per table, re-reads each row to confirm round-trip before committing, and is idempotent (second run: zero changes; after one successful run the unmarked count is zero). Identifies rows by table/column/ID only — no value or fragment ever printed or logged.
4. **Startup report** (report-only, stored-endpoint-check pattern): when a key is configured, count **unmarked rows** (`COUNT(*) WHERE col IS NOT NULL AND col NOT LIKE 'enc:v1:%'` — 11 columns, 5 tables, NO decrypt, no PBKDF2, no row cap needed). WARNING naming the command; never blocks startup; never logs values. "Unmarked" covers legacy plaintext, ambiguous values, and pre-v0.16.40 ciphertext; the command sorts them into the three classes.
5. **README section** "Turning on encryption on an existing install": set the key, dry run, `--apply`, only then `LETTA_REQUIRE_ENCRYPTION=true`. Document the `docker exec` form and the downgrade warning.

**Tables**: `AgentEnvironmentVariable.value_enc`, `SandboxEnvironmentVariable.value_enc`, `Provider.api_key_enc`+`access_key_enc`, `MCPServer.token_enc`+`custom_headers_enc`, `MCPOAuth` (authorization_code, access_token, refresh_token, client_secret).

**Witnesses (RED on v0.16.39, per the reviewer's table):**
1. Write path: unchanged legacy plaintext re-sent → stored as marked ciphertext, reads back identically. RED.
2. F-A: ambiguous legacy row re-sent through `PATCH /v1/agents/{id}` → today 500, after: 200 + stored marked. RED. (This is also the operator's documented fix for ambiguous rows without the override flag.)
3. Command: dry-run classes correct across all 5 tables; `--apply` stores everything marked and round-trips each value; second `--apply` changes nothing. RED (no command).
4. Ambiguous rows block `--apply`; override + `--yes` encrypts them. RED.
5. Marked value + wrong key raises, naming no value. RED (no marker).
6. Startup report counts unmarked rows without decrypting, gated on the key. RED.
7. No secret values in stdout, stderr, or the server log across witnesses 2-5.
8. Rig: no key, store a secret, restart with a key, run the command, a tool reads the secret correctly. RED. Rig mechanics: two server generations (compose restart with the key env set) + `docker compose exec` for the command — budget as a SEPARATE rig script, required for v0.16.40 and for any later release touching `secret.py` or the managers; don't drop it.

**Consumer impact**: Delta — until adoption, the D-3 two-step re-sync works on v0.16.39; after adoption, normal credential re-sync + one command run. Nabla/Epsilon — no action during filming; pick up at next re-pin. The v0.16.40 consumer notice carries the downgrade warning.

One commit per item, each with its own witnesses, as in C-1.

**U-5 (L-10) SSRF in the server-side image fetch.** `letta/helpers/message_helper.py`, `_fetch_image_from_url`: fetches any http/https URL with `follow_redirects=True`; nothing blocks loopback, RFC 1918, link-local, or the cloud metadata address 169.254.169.254. Any authenticated caller can put such a URL in an image message and the response is fed to the model. Fix: (1) resolve the hostname before connecting; reject loopback, private, link-local, unique-local (IPv6) and multicast addresses, plus `0.0.0.0` and `::`; connect to the validated IP, not the name (DNS rebinding between check and connect fails). (2) No automatic redirects — follow at most three manually, re-running the address check each hop. (3) Require `image/*` content type; cap response size (10 MB suggested, streamed, aborted past the cap). (4) Operator escape hatch `LETTA_IMAGE_FETCH_ALLOW_PRIVATE=true` for lab setups serving images internally; defaults off, logs a startup WARNING when on. Witnesses (RED on the current tree): loopback URLs rejected (`http://127.0.0.1:8283/v1/health`, `http://[::1]/`); `http://169.254.169.254/latest/meta-data/` rejected; a 302 from an allowed public host to `127.0.0.1` rejected (local test server); non-image content type rejected; oversize body aborted; a normal public image URL still works. Docs: add L-10 to the README's "Known security holes" until it ships, then mark closed with the version.

**U-6 Insecure mode binds to loopback only.** `LETTA_SERVER_SECURE=false` disables auth but the server can still bind `0.0.0.0` — an unauthenticated API on the network. Fix: in insecure mode, refuse to start if the bind host isn't loopback (`127.0.0.1`, `::1`, `localhost`); the error names the fix ("set `LETTA_SERVER_PASSWORD`, or bind to 127.0.0.1"). Witnesses: insecure+`0.0.0.0` refuses to start; insecure+`127.0.0.1` starts; secure+`0.0.0.0` starts; rig still passes.

**REV 5 (review P-2) — container decision settled: REQUIRE secure mode in the container image.** In a container, a `0.0.0.0` bind is what makes the port reachable from outside it, so insecure mode in a container is exactly the case U-6 exists to prevent; an opt-in env var is one more setting people copy-paste into compose files and forget. Implementation: the image's entrypoint refuses `LETTA_SERVER_SECURE=false` unless the bind host is loopback (preserves `docker run --network host` with a loopback bind for local development); the error names the fix: set `LETTA_SERVER_PASSWORD`. Pre-implementation check: whether any consumer's compose file runs the container in insecure mode — Delta pins 0.16.24, which predates secure mode, so its compose is the one to look at. If one does, flag it in the evidence doc and that consumer's next notice; do NOT loosen the rule to accommodate it.

**U-7 Origin and CORS audit.** A localhost API is reachable by browser-based attacks (DNS rebinding, cross-site requests); Letta Code rejects any request carrying an `Origin` header. Our CORS list lost the upstream origin in B-2 but the rest is unaudited. Audit: report the effective CORS origins and whether credentials are allowed; what happens to a request with an unexpected `Origin` and a valid password; what happens to a request whose `Host` header names a non-local domain (DNS-rebinding signature). Fix if gaps: reject requests with an `Origin` not on the allowlist; add an optional `Host` header allowlist defaulting to localhost names plus the configured bind host. Witness: rejected requests for a foreign Origin and a foreign Host; allowed for neither. Write the audit result into the v0.16.40 evidence doc even if nothing needs changing.

**U-8 Telemetry audit (backs a marketing claim).** Code-read says LettaLocal sends nothing off the machine by default (Sentry only with `SENTRY_DSN`, OTEL only with an endpoint, B-2 removed upstream domains) — but that was a read, not an audit. (1) Static: grep for every outbound HTTP client construction and hard-coded URL; classify each as operator-configured, model/provider traffic, or default phone-home. (2) Live witness: rig check — start the server with no provider keys and no telemetry settings, run the quick-start flow against local Ollama, capture outbound connections (tcpdump/ss in the container, or a deny-all egress network with logging); the only allowed destinations are Postgres, the local inference endpoint, and the embedding endpoint. (3) Record in the evidence doc; if clean, "sends no telemetry by default" goes into the FAQ citing the rig check.
